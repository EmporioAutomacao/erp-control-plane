Arquitetura da plataforma

🏗️ Como o tráfego chega ao ERP do cliente

A plataforma usa Cloudflare Tunnel — uma conexão de saída permanente entre o servidor e a Cloudflare. Nenhuma porta precisa estar aberta no servidor.

Fluxo completo de uma requisição:

Browser → Cloudflare Edge (HTTPS) → cloudflared (tunnel) → Traefik :80 → {slug}_web (ERP)
ComponenteResponsabilidade
Cloudflare Edge Termina o HTTPS do browser. Encaminha para o servidor via tunnel (sem precisar de porta aberta).
cloudflared (serviço Swarm) Mantém a conexão de saída com a Cloudflare. Recebe tráfego e encaminha para http://traefik_traefik:80 internamente.
Traefik (serviço Swarm) Roteador HTTP interno. Lê labels dos serviços Docker e roteia pelo cabeçalho Host. Ex: Host(`slug.ararasuite.com.br`) → {slug}_web.
{slug}_web Container Django do ERP do cliente. Cada cliente tem seu stack isolado (web, db, redis).
💡 Por que o tunnel? O servidor não precisa de IP público acessível nem de portas abertas no firewall. Toda conexão externa sai do servidor para a Cloudflare — nunca entra diretamente. Isso é mais seguro e funciona mesmo atrás de NAT.

Fluxo de um novo cliente

1
Cliente preenche o formulário em /comecar/ ou é criado manualmente em Admin → Clientes → Adicionar.
2
Um signal post_save dispara automaticamente a task task_provisionar_cliente no Celery.
3
O motor gera .env e stack.yml em CLIENTES_BASE_PATH/{slug}/ e executa docker stack deploy. O stack inclui: {slug}_web (ERP), {slug}_db (PostgreSQL+pgvector), {slug}_redis.
4
Aguarda o serviço {slug}_web ficar Running (até 180s) e /health/ responder 200. Status muda para ativo.
5
A task task_enviar_email_boas_vindas envia e-mail HTML com URL, usuário admin e senha inicial.

Domínio custom

🌐 Como funciona

Todo cliente tem um subdomínio padrão: {slug}.ararasuite.com.br. O campo Domínio custom (seção Infraestrutura) permite que o cliente use também o próprio domínio — os dois funcionam em paralelo.

O que o sistema configura automaticamente:

ComponenteO que é configurado
Django ALLOWED_HOSTS e CSRF_TRUSTED_ORIGINS incluem o domínio custom
Traefik Router {slug}-erp-custom com Host(`dominio`) → mesmo serviço {slug}-erp
Cloudflare Tunnel Ingress rule: dominio → http://traefik_traefik:80
DNS Cloudflare CNAME @ → {tunnel-id}.cfargotunnel.com (proxy ativo)

📋 Fluxo completo de ativação

1
Preencha Domínio custom (ex: meaempresa.com.br) e salve.
2
Clique em ⚙ Aplicar Configurações — Django e Traefik passam a aceitar o domínio (~30s).
3
Clique em ☁ Configurar Cloudflare — adiciona o domínio ao tunnel e cria o CNAME no DNS.
4
Se a zona foi criada agora: informe ao cliente os nameservers exibidos na mensagem — ele precisa trocá-los no registrador (Registro.br, GoDaddy, etc.). Propaga em 1–24h.
Se a zona já estava ativa: o CNAME propaga em segundos e o domínio já funciona.
5
Após propagação, o ERP responde em https://meaempresa.com.br com HTTPS automático pela Cloudflare.

⚠️ Casos especiais

SituaçãoComportamento
CNAME já aponta para o tunnel correto Nenhuma alteração. Idempotente.
Existia registro A/AAAA antigo (no apex ou no www) O sistema remove os registros A e AAAA e cria o CNAME automaticamente.
Já existia um CNAME www apontando para outro host O sistema atualiza o CNAME existente para o tunnel (busca sempre pelo FQDN www.dominio). Antes da v0.0.27 isso falhava com 400: record with that host already exists.
Zona existe em outra conta Cloudflare Cloudflare retorna erro "already exists" — o domínio precisa ser transferido para esta conta.
Domínio custom removido (campo limpo) "Aplicar Configurações" retira o domínio do ALLOWED_HOSTS e das labels Traefik. O registro DNS e a entrada no tunnel não são removidos automaticamente — faça isso manualmente em Cloudflare → Zero Trust → Tunnels.

Cloudflare — configuração do CP

☁ Token de API necessário

Acesse Configurações → Cloudflare para configurar o token. O token precisa das seguintes permissões:

PermissãoEscopoPara que serve
Zone:Read All Zones Listar e encontrar zonas dos clientes
DNS:Edit All Zones Criar/atualizar registros CNAME
Cloudflare Tunnel:Edit All Accounts Adicionar hostnames ao ingress do tunnel

Criar em: Cloudflare → My Profile → API Tokens → Create Token → Custom Token.

⚠️ Token deve ser escopo "All Zones" — um token restrito a ararasuite.com.br não consegue gerenciar domínios de clientes.

☁ Nome do Tunnel

No campo Nome do Tunnel, informe o nome exato do Cloudflare Tunnel que o servidor usa.

Para encontrar o nome:

  • Cloudflare → Zero Trust → Networks → Tunnels
  • O nome aparece na lista de tunnels ativos

Se o campo ficar vazio, o sistema usa o primeiro tunnel ativo encontrado na conta. Se houver apenas um tunnel, não é necessário preencher.

Para verificar no servidor:

docker service ls | grep cloudflared

☁ O que o botão "Verificar token" faz

Em Configurações → Cloudflare, o botão chama GET /user/tokens/verify na API da Cloudflare e exibe o status do token.

Mensagens possíveis:

  • Token válido — status: active → token OK
  • Token inválido (401) → token errado ou expirado
  • Token inválido (403) → token é Global API Key — use API Token
Nunca use a Global API Key. Use sempre um API Token criado com as permissões específicas.

Infraestrutura e configurações

🔄 Recriar cliente do zero

  • Clique em Destruir — remove stack, volumes e todos os dados.
  • Crie um novo cliente com o mesmo slug (ou diferente).
  • O provisionamento dispara automaticamente.

Se quiser manter o banco, use Re-provisionar — nunca Destruir.

Resumo de segurança:

  • Aplicar Configurações → não toca no banco seguro
  • Re-provisionar → preserva banco seguro c/ backup
  • Destruir → apaga tudo irreversível

✉️ Configuração de e-mail

Acesse Configurações → E-Mail para configurar o servidor SMTP.

  • Usar TLS — padrão para porta 587
  • Verificar SSL — desmarque se o certificado não corresponder ao hostname (hospedagem compartilhada)
  • Botão "Enviar e-mail de teste" — envia imediatamente (síncrono)
⚠️ A configuração do .env não é usada. Apenas o registro salvo no banco vale para envio de e-mails.

⏱️ Worker Celery

Em produção o container celery processa as tasks automaticamente.

Em desenvolvimento local, suba o worker manualmente:

.\venv\Scripts\python.exe -m celery -A core worker --loglevel=info --pool=solo
⚠️ No Windows, use sempre --pool=solo. O pool padrão (prefork) usa multiprocessing que falha no Windows com WinError 5/6. Em produção Linux este parâmetro não é necessário.

Após mudanças no código, reinicie em produção com novo docker stack deploy. As tarefas periódicas estão em Agendamentos → Tarefas Periódicas.

🖥️ Hosts de infraestrutura

Cada cliente pode ser associado a um HostInfraestrutura. O campo Região define o placement do Docker Swarm:

node.labels.region == {regiao}

Para ver os labels de um nó do Swarm:

docker node inspect {node-id} --format '{{.Spec.Labels}}'

Para adicionar um label de região a um nó:

docker node update --label-add region=anapolis {node-id}

Backup e restauração

💾 O que é incluído no backup

Entrada no arquivoOrigemConteúdo
db.sql docker exec {slug}_db pg_dump --clean --if-exists Dump completo do PostgreSQL (inclui extensão pgvector/RAG)
media/ docker cp {slug}_web:/app/media/. Arquivos enviados pelos usuários (uploads, imagens, documentos)
config/ CLIENTES_BASE_PATH/{slug}/ .env e stack.yml do cliente

O arquivo é salvo em CP_BACKUP_DIR/clientes/{slug}/backup_{slug}_{timestamp}.tar.gz.
Retenção: 3 backups por cliente. O mais antigo é removido automaticamente.

💾 Como usar o backup

1
Na página do cliente, role até a seção Backups e clique em 💾 Novo Backup.
2
A barra de progresso é atualizada em tempo real a cada 2s. Ao concluir, a página recarrega automaticamente.
3
O backup aparece na tabela com badge de status: Concluído libera o ⬇ Baixar; Erro não gera arquivo.
4
Para restaurar, clique em ↩ Restaurar e confirme o diálogo. O ERP fica indisponível durante a restauração (~1–2 min).
⚠️ O backup nunca fica "Concluído" com um arquivo vazio. Cada etapa (banco, mídia, config) que não encontra o container/diretório, ou cujo comando falha (pg_dump/docker cp), vira um aviso:
  • Erro — nenhuma etapa capturou conteúdo; o arquivo é removido. É o que acontece em dev local sem os containers {slug}_db/{slug}_web ativos.
  • Concluído com ⚠ — pelo menos uma etapa funcionou; as que falharam ficam resumidas ao lado do tamanho/downloads na lista de backups.
A restauração segue o mesmo princípio: se o banco não puder ser restaurado (container ausente, psql falhou) ou a mídia não puder ser copiada, aparece um segundo aviso ⚠ Última restauração: … abaixo do backup na lista — mesmo se o restante tiver funcionado. Sem aviso = restauração completa sem erros.

⬆ Importar backup manualmente

Clique em ⬆ Importar Backup (ao lado de "Novo Backup") para enviar um .tar.gz/.tgz já existente do seu PC — útil para backups migrados de outro ambiente ou feitos antes desta funcionalidade existir.

O arquivo é gravado como manual_{slug}_{timestamp}.tar.gz e o backup entra na lista com a tag manual ao lado do badge de status. Backups manuais não contam para o limite de retenção de 3 e nunca são apagados automaticamente.

⚠️ A validação é só estrutural (existência de db.sql/media/ dentro do tar) — não garante compatibilidade com a versão do ERP do cliente. Arquivos muito grandes (vários GB) podem falhar em produção pelo timeout do worker (~120s) durante o envio.
💡 Diagnóstico rápido: se um domínio custom não responde, verifique em ordem: (1) o serviço está Running no Swarm (docker service ps {slug}_web); (2) as labels Traefik estão aplicadas (docker service inspect {slug}_web); (3) o tunnel tem o hostname no ingress (Cloudflare → Zero Trust → Tunnels → Public Hostnames); (4) o CNAME no DNS aponta para o tunnel.

Sincronização — ativação do SyncAgent

🔌 O que é

O SyncAgent é um serviço Windows instalado na máquina do cliente (PDV local) que sincroniza operadores, produtos, clientes e vendas com o ERP daquele cliente. Ele se conecta ao ERP por HTTPS + token técnico — o CP não fala direto com o agente.

A ativação é feita uma vez, na máquina do cliente, em http://127.0.0.1:47891/setup, com um código de ativação gerado no admin do ERP (API de Sincronização → Códigos de Ativação → Gerar).

⚙ Pré-requisitos no CP antes de ativar

1
Cliente com imagem ERP ≥ 0.0.96 — use "Atualizar versão" na página do cliente.
2
Clicar em ⚙ Aplicar Configurações — injeta CP_CLIENTE_ID/CP_CLIENTE_NOME no serviço, sem os quais o ERP bloqueia a geração de códigos.
3
Conferir a versão pelo rodapé de https://{slug}.ararasuite.com.br/admin/ ou por docker service inspect {slug}_web (campo da imagem).
4
No admin do ERP → API de Sincronização → Instalações do SyncAgent → apagar instalações órfãs do cliente (coluna "Visto por último" vazia, de códigos queimados antes).

🚑 Erros de ativação e correções

Mensagem / codeCausaCorreção
Configure o ID do cliente no CP em Configurações > Plano… ERP sem o vínculo com o CP (CP_CLIENTE_ID ausente). Botão ⚙ Aplicar Configurações no cliente. Requer imagem ERP ≥ 0.0.94.
invalid_response — must use HTTPS outside local development ERP < 0.0.96 devolvia a URL da API em http:// (o Traefik reescreve X-Forwarded-Proto). Atualizar o ERP para ≥ 0.0.96. O código já foi consumido → apagar a instalação órfã no ERP e gerar um novo.
activation_code_used Código já consumido (tentativa anterior, ou envio duplo do formulário na tela do agente). Gerar código novo. Preferir gerar sem "ID da instalação" — o ERP gera um e evita colisão.
activation_code_expired / activation_code_revoked Fora da validade (5 min – 24 h) ou revogado. Gerar um novo e usar em seguida.
tenant_invalid Código gerado antes de o CP estar resolvido no ERP. Aplicar Configurações no CP; depois gerar o código.
erp_unreachable / activation_timeout A máquina do agente não alcança o ERP (rede, firewall, DNS, URL errada). Testar https://{slug}.ararasuite.com.br/health/ pelo navegador na própria máquina do agente.
Client certificate is required (depois de ativar, agente fica degraded) O appsettings.json do agente tem RequireMutualTls=true, mas o ERP (Traefik/Cloudflare) não faz mTLS. Na máquina do cliente: "RequireMutualTls": false na seção ErpSecurity do appsettings.json e reiniciar o serviço AraraSuiteSync. Instalador ≥ 1.3.2 já usa false.
23505 … operators_login_key (import de operadores) Banco local do agente reaproveitado entre clientes diferentes. Agente ≥ 1.3.1 (import resiliente). Instalação nova não apresenta.
Aguardando ativação com o ERP (not_provisioned) Estado normal — a ativação ainda não foi concluída. Concluir a ativação em http://127.0.0.1:47891/setup na máquina do cliente.
⚠️ O código de ativação é de uso único. Toda tentativa que chega a criar a SyncInstallation no ERP queima o código, mesmo que o agente rejeite a resposta depois — por isso quase sempre é preciso apagar a instalação órfã e gerar um código novo a cada correção. Guia técnico completo: docs/infra/sync-agent-ativacao-troubleshooting.md (repo erp).

⬆ Curadoria de versões do PDV Local por cliente (painel de controle)

Desde a versão 1.6.0 do PDV Local, o botão "Atualizar App" na bandeja do cliente mostra uma lista de versões — não mais "a versão atual" única. Quem decide quais versões cada cliente pode escolher é este painel, na página do próprio Cliente (aba "Versões do SyncAgent/PDV"), não mais direto no admin do ERP de cada cliente.

💡 O ERP de cada cliente aplica as travas de verdade — o CP só cura o que pode ser oferecido. Downgrade nunca é oferecido (mesmo que uma versão antiga esteja marcada aqui) e uma versão que exija um ERP mais novo aparece desabilitada com o motivo na bandeja, nunca aplicável.
1
Atualizar o catálogo (uma vez, vale pra todos os clientes) — Clientes → Versões do Agente → botão "🔍 Verificar novas versões no GitHub". Varre github.com/EmporioAutomacao/pdv-local/releases sozinho e cria/atualiza versão, URL e SHA256 de cada Release publicado — nada pra digitar. Pode clicar de novo a qualquer momento (não duplica nem desfaz nada). Só preencha manualmente "Versão mínima do ERP exigida" na versão, se ela precisar de recursos do ERP que ainda não existem em versões antigas — o GitHub não sabe disso, e uma nova verificação nunca apaga o que você já preencheu aí. (Alternativa por linha de comando, sem depender do GitHub: python manage.py register_versao_agente --versao X.Y.Z --download-url <zip> --sha256 <hash>.)
2
Permitir para o cliente — na página do Cliente, aba "Versões do SyncAgent/PDV", adicione a versão em "Versões permitidas" e salve. Isso dispara sozinho o envio pro ERP daquele cliente (ou clique em ⇪ Sincronizar Versões com o ERP pra forçar na hora).
3
Na máquina do cliente: bandeja → Atualizar App → o dono da loja escolhe entre as versões permitidas e não-bloqueadas. Baixa o .zip, confere o SHA256 e roda self-update.ps1 (backup + troca + rollback automático). appsettings.json e credenciais são preservados.
SituaçãoCausaCorreção
Botão "⇪ Sincronizar Versões" demora e volta com erro de timeout/SSL Normal em ambiente local de dev sem Traefik/TLS na frente do ERP de teste (o CP sempre chama https://{subdomínio}). Em produção, o Traefik do cliente termina o TLS normalmente. Nada a corrigir em produção. Em dev local, teste o endpoint direto por IP/porta do container (ver docs/registry/release-curadoria-versoes-syncagent.md).
Botão de sincronizar avisa "sem segredo de integração ainda" Cliente provisionado antes desta funcionalidade — não tem integracao_secret gerado. Clique em ⚙ Aplicar Configurações uma vez (gera o segredo e o envia pro ERP), depois sincronize as versões.
Bandeja mostra Nenhuma versão publicada foi encontrada no ERP Nenhuma versão permitida chegou ainda nesse ERP (nunca sincronizou, ou todas foram removidas da curadoria). Passos 1–2 acima. Conferir também que o agente está no ERP certo (/status → erp_api_base_url).
Versão aparece na bandeja mas desabilitada "Versão mínima do ERP exigida" daquela versão é maior que a versão real do ERP do cliente. Atualizar o ERP do cliente primeiro ("Atualizar versão" na página do cliente), ou permitir uma versão do PDV Local compatível.

Guias técnicos: docs/registry/release-curadoria-versoes-syncagent.md (este repo), docs/infra/sync-agent-auto-update.md (repo erp). Publicar Release novo do PDV Local: git tag vX.Y.Z && git push origin vX.Y.Z no pdv-local (workflow builda e publica sozinho).

🔗 Conexões Arpa Control (geridas pelo agente)

A partir do SyncAgent 1.5.0, as conexões com bancos Arpa Control são configuradas no dashboard do agente, na máquina do cliente (http://127.0.0.1:47891/config/arpa) — uma por Loja/Estoque, com toggles Produtos / Clientes / Estoque / Vendas / Financeiro. Não mais no appsettings.json nem no admin do ERP.

  • O agente reporta as conexões no heartbeat (sem senha). O ERP cria/atualiza linhas em Conexões Arpa Control marcadas Gerido pelo SyncAgent — somente leitura (editar só no agente); Empresa/Estoque/Conta de Caixa seguem editáveis para o admin completar o mapeamento.
  • Conexões geridas pelo agente não podem ser excluídas no admin — somem quando removidas no dashboard do agente. Conexões manuais (lojas sem SyncAgent, sync direto do ERP) não são tocadas.
  • As views sync_export.* no banco Arpa de cada cliente são criadas pelo botão "Preparar views" do dashboard, ou pelo fluxo de diagnóstico quando o schema real diverge.

Guias: docs/infra/sync-agent-arpa.md (repo erp), docs/arpa-collector-piloto.md (repo pdv-local).
