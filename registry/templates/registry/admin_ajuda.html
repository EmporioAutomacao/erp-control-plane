⚡ Central de Ajuda — AraraSuite CP

Guia rápido para gerenciar clientes, provisionamento, e-mail e infraestrutura.

Fluxo de um novo cliente

1
Cliente preenche o formulário em /comecar/ ou é criado manualmente em Admin → Clientes → Adicionar.
2
Um signal post_save dispara automaticamente a task task_provisionar_cliente no Celery.
3
O motor gera .env e stack.yml em CLIENTES_BASE_PATH/{slug}/ e executa docker stack deploy.
4
Aguarda o serviço {slug}_web ficar Running (até 180s). Status muda para ativo.
5
A task task_enviar_email_boas_vindas envia o e-mail HTML com URL, usuário e senha inicial.

🏷️ Status do cliente

Aguardando Provisionando Ativo Trial Atualizando Suspenso Erro Cancelado

Em caso de erro_provisao, o Celery retenta até 3× com 60s de delay. Se persistir, use o botão Re-provisionar na página do cliente.

⚙️ Ações de provisionamento

  • ⚙ Aplicar Módulos — Atualiza a variável MODULOS_ATIVOS no .env do cliente e reinicia o serviço web via docker service update. Não toca no banco de dados. Use sempre que adicionar ou remover módulos na aba Plano.
  • Re-provisionar — Executa o docker stack deploy novamente. Não apaga o banco: o volume pgdata é preservado e a senha existente é reutilizada. ⚠️ Risco apenas se o .env for apagado manualmente — nesse caso a senha gerada não coincide com a do volume e o Postgres recusa conexão. Faça backup antes se houver dúvida.
  • Destruir — Remove o stack e apaga os volumes (pgdata, media, backups), os arquivos e o registro do banco. Ação irreversível — todos os dados do cliente são perdidos.
  • ✉ Reenviar Boas-vindas — Reenfileira o e-mail HTML de boas-vindas com os dados de acesso atuais.

🧩 Ativar e desativar módulos

Cada cliente pode ter módulos diferentes habilitados. O fluxo é:

  • Na página do cliente, aba Plano, selecione os módulos em "Módulos ativos" e salve.
  • Clique em ⚙ Aplicar Módulos — o serviço reinicia em segundos com os novos módulos.

O que cada cenário faz:

  • Serviço rodando — docker service update --env-add MODULOS_ATIVOS=... faz rolling restart sem perda de dados.
  • Serviço não provisionado — os módulos ficam salvos no .env e serão aplicados no próximo provisionamento.

No ERP: módulos desativados somem do menu lateral e ficam sem acesso. Módulos ativos são lidos da variável de ambiente MODULOS_ATIVOS na inicialização do servidor.

🔑 Acesso ao ERP do cliente

Na página do cliente, o painel "Acesso ao ERP" exibe:

  • URL — subdomínio ou domínio customizado
  • Usuário — sempre admin
  • Senha inicial — extraída do log de provisionamento etapa criar_superuser

A senha só aparece se o provisionamento foi concluído com sucesso.

✉️ Configuração de e-mail

Acesse Configurações → E-Mail para configurar o servidor SMTP.

  • Usar TLS — padrão para porta 587
  • Verificar SSL — desmarque se o certificado não corresponder ao hostname (ex: servidores de hospedagem compartilhada)
  • Botão "Enviar e-mail de teste" — envia imediatamente (síncrono) para o e-mail remetente configurado

⚠️ A configuração do .env NÃO é usada. Apenas o registro do banco vale.

⏱️ Worker Celery

Em produção o container celery processa as tasks automaticamente.

Em desenvolvimento local, suba o worker manualmente:

.\venv\Scripts\python.exe -m celery -A core worker --loglevel=info

Tarefas periódicas ficam em Agendamentos → Tarefas Periódicas. O worker também precisa do beat para executá-las: adicione -B ou suba um container celery-beat separado.

🖥️ Hosts de infraestrutura

Cada cliente é alocado em um HostInfraestrutura. O placement do Docker Swarm usa:

node.labels.region == {regiao}

Certifique-se de que o nó Swarm tem o label correto. Para ver os labels:

docker node inspect {id} --format '{{.Spec.Labels}}'

🔄 Recriar cliente do zero

  • Clique em Destruir — remove stack, volumes e todos os dados.
  • Crie um novo cliente com o mesmo slug (ou diferente).
  • O provisionamento dispara automaticamente.

Se quiser manter o banco (pgdata), use Re-provisionar — nunca Destruir.

Resumo da diferença:

  • Re-provisionar → preserva banco ✔
  • Destruir → apaga banco ✘
  • Aplicar Módulos → não toca no banco ✔

📋 Logs de provisionamento

Na página de cada cliente há o inline "Logs de Provisionamento" com todas as etapas:

  • gerar_arquivos — gerou .env e stack.yml
  • deploy_stack — executou docker stack deploy
  • aguardar_servico — aguardando container Running
  • aguardar_http — aguardando /health/ 200
  • criar_superuser — senha inicial gerada aqui
💡 Dica: Sempre que fizer alterações no código e precisar que o worker Celery use o código novo, reinicie o container:
docker compose -f docker-compose.dev.yml restart celery
Em produção, atualize o stack com docker stack deploy apontando para a nova imagem.
